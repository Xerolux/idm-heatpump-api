# API 1.0 Transport Handoff

<current_state>

The API 1.0 work was paused immediately after the read-only architecture and release audits. This branch, `Codex/api-1.0.0-transport`, starts from API `v0.9.1` at `377e0ce`. Only handoff files have been added; no runtime, tests, version metadata, workflow or documentation implementation has started.

The related add-on baseline is released as `v0.11.0-beta.1` at `a423f8c`. Its current tmodbus bridge passes 21 focused tests against API 0.9.1, but subclasses `IdmModbusClient` and relies on private members.

</current_state>

<decisions_made>

- Direct Pymodbus remains the compatible default transport; API 1.0 is additive for existing consumers.
- `modbus-connection` and `tmodbus` are not API dependencies. They remain implementation details of the Home Assistant add-on.
- The API owns register maps, codecs, batching, model detection, retry policy and write safety. Injected transports expose only lifecycle plus raw words.
- The add-on should become a thin constructor/diagnostics wrapper and stop overriding API private methods and fields.
- `v0.10.1` and `v0.11.0-beta.1` remain on the exact API 0.9.1 pin; only the new `0.11.0-beta.2` will explicitly pin stable API 1.0.0.

</decisions_made>

- Do not turn the existing protected subclass hooks into the public 1.0 contract.
- Do not add a hard API dependency on Home Assistant, `modbus-connection` or tmodbus.
- Do not treat transient device response codes 5/6/10/11 as unsupported individual registers.
- Do not stack backend and API retries for server-busy code 6.
- Do not claim a stable 1.0.0 is exclusively installable by Beta 2.
- Do not publish until both legacy Pymodbus and the real add-on transport adapter pass.
- Do not alter the register schema as part of the Ruff formatting repair.
