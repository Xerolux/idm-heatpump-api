## Repository baseline used for comparison

Comparison was made against the current register definitions in
`idm_heatpump/registers.py` and the Markdown reference in
`docs/Modbus-Register.md`.

Important implementation details observed:

- Heating-circuit registers are generated per circuit A-G.
- With detected `model_info`, only circuits listed in

- GLT registers `1690-1722` are always added by the current map builder.
- Optional PV, cascade, solar, and ISC blocks depend on detected features when
  `model_info` is available.

### RESOLVED — `detect_model()` non-contiguous heating-circuit detection (fixed 2026-07-16)

Device 2 has heating circuits **A and D** physically installed
(user-confirmed), but `detect_model()` returned only `['A']`. The raw
evidence on device 2 shows why — both presence discriminators agree:

| circuit | flow_temp (1350+i·2) | active_mode (1498+i) | truth |
| --- | --- | --- | --- |
| A | 27.6 °C (real) | 0x0000 (real) | **installed** |
| B | -1.0 (sentinel) | 0xFFFF (sentinel) | not installed |
| C | -1.0 (sentinel) | 0xFFFF (sentinel) | not installed |
| D | 26.9 °C (real) | 0x0000 (real) | **installed** |
| E | -1.0 (sentinel) | 0xFFFF (sentinel) | not installed |
| F | -1.0 (sentinel) | 0xFFFF (sentinel) | not installed |
| G | -1.0 (sentinel) | 0xFFFF (sentinel) | not installed |

Root cause (was in `idm_heatpump/client.py`): the detection loop probed
only the flow-temperature register (`1350 + i*2`) and broke after two
consecutive `-1.0` sentinels (`_DETECT_EMPTY_SLOT_STOP_THRESHOLD = 2`).
On device 2 that path was A(real) → B(sentinel) → C(sentinel) → break, so
circuit **D (real, 26.9 °C) was never probed**. This is the same symptom
class reported in HASS issue #44 (wrong model/circuit detection).

**Fix merged to main** (PR #48, commit `919c167`, 2026-07-16):

- Heating-circuit detection now scans **all seven slots A-G** without
  early-break (zone-module detection keeps its early-break; those slots
  are always contiguous).
- A second presence signal — the **active operating-mode register**
  (`1498+i`, UCHAR) — is now probed. A circuit counts as active when its
  flow temperature is a real value (not `-1.0`) **OR** its active-mode
  register is not the UCHAR `0xFFFF` "not configured" sentinel. This
  ODER-logic catches circuits that report `-1.0` on flow temperature
  (e.g. pump off, no flow sensor) while still being physically configured.
- Note on register choice: the originally-considered `hc_mode` register
  (1393+i) was rejected because `hc_mode == 0` means "standby/off", not
  "not present" — on device 2 circuit A has `hc_mode == 0` yet is
  installed. The `active_mode` register (1498+i) is the reliable signal:
  `0xFFFF` (UCHAR 255) = "not configured".

Verified live on device 2: `['A']` → **`['A', 'D']`**. Tests: pytest 269
passed (+2 regression guards), Ruff clean, mypy clean, CI green on the
PR and on the merge commit. See CHANGELOG.md `[Unreleased]`.

## Live-Test Results (2026-07-16, device 192.168.178.103)

Read-only verification against a live IDM heat pump at `192.168.178.103`
(Modbus TCP, port 502, slave ID 1). Only READ function codes (FC3 holding
and FC4 input) were used. No writes were performed at any point.

Device identity (confirmed via `IdmModbusClient.detect_model()`):

- **Controller: Navigator 10** (`model_name == "Navigator 10"`).
- Active heating circuits: `['A']`; zone modules: 0.
- Features detected: solar, isc, pv, heating_circuits. **Cascade: not present.**
- Firmware reported by `detect_model()`: **`None`** — because the API reads
  the firmware register at address **4120**, which this device rejects with
  `IllegalAddress` (see Open Point 2). The actual firmware string reported by
  the local web UI is `NAV10_20.24-880-g265e09c4a`.
- **Important:** earlier analysis drafts referred to this device as Navigator 2.
  That was incorrect. All findings below are from a Navigator 10 unit and must
  be interpreted as Nav10 evidence, not Nav2 evidence.

Environment notes:

- FC3 and FC4 return **identical** data on this device for every probed
  address. The device does not distinguish holding vs. input registers.
- FLOAT decode convention confirmed: IDM FLOAT = IEEE-754, low word first.
  Example: `outdoor_temp` @1000 = raw `[43755, 16882]` -> `30.333` (°C),
  which is a plausible July ambient temperature.
- Baseline sanity: `storage_temp` @1008 -> `69.078`, `hc_a_flow_temp` @1350
  -> `28.730`, `system_mode` @1005 -> `1`, `hc_a_mode` @1393 -> `2`. All
  realistic; connection and decode order are correct.
- Sentinel observed: raw `[0x0000, 0xBF80]` decodes (low-word-first) to
  exactly `-1.0`. This matches the screenshot value `-1` and is treated as
  the "unavailable / no GLT value" sentinel throughout the PV/GLT area.

### Open Point 1 — unnamed PV/EM IDs 68, 70, 72, 80

All four addresses are readable FLOAT (count=2). The decoded value is the
`-1.0` sentinel on all of them, identical to the screenshot value `-1`.

| ID | count=1 (UINT16) | count=2 raw words | decoded FLOAT (low-first) | conclusion |
| ---: | ---: | --- | ---: | --- |
| 68 | 0x0000 (0) | `[0x0000, 0xBF80]` | **-1.0** | FLOAT, currently unavailable (sentinel) |
| 70 | 0x0000 (0) | `[0x0000, 0xBF80]` | **-1.0** | FLOAT, currently unavailable (sentinel) |
| 72 | 0x0000 (0) | `[0x0000, 0xBF80]` | **-1.0** | FLOAT, currently unavailable (sentinel) |
| 80 | 0x0000 (0) | `[0x0000, 0xBF80]` | **-1.0** | FLOAT, currently unavailable (sentinel) |

Datatype determination:

- `count=2` succeeds and decodes to a clean `-1.0`; `count=1` returns the
  low word `0x0000` only. The pair `[0x0000, 0xBF80]` is exactly the
  IEEE-754 representation of `-1.0` in low-word-first order, so the
  datatype is **FLOAT32 (2 registers)**, matching the neighboring PV/EM
  block (74/76/78/82, all FLOAT32).
- They respond on both FC3 and FC4 like the rest of the PV/EM block.
- Compare documented neighbor `pv_surplus` @74: raw `[0xD0E6, 0x4124]` ->
  `10.3010` kW (real value), proving the block carries live FLOAT data; the
  `-1.0` at 68/70/72/80 is therefore a true "not configured / no value"
  state, not a decode artefact.

**Name still unknown.** The numeric addresses and FLOAT type are confirmed,
but the UI name, unit, and write semantics (RW shown in the screenshot)
remain undetermined from Modbus alone. Do not write until the official
name/range/sentinel semantics are known. The `-1.0` sentinel is consistent
with the existing `MODEL_DETECTION_UNAVAILABLE` handling.

  not from Modbus.
- `firmware_version @4120` (the current repository address) returns
  `IllegalAddress` on this Nav10 unit, which is why `detect_model()`
  returned `firmware_version: None` and why the code disables that register
  by default.
- Address **4116** is readable (`[0x9840, 0x2000, 0x00FF, 0x0000]`, count ≤ 4
  only), but **it is almost certainly NOT the firmware version.** The raw
  bytes do not encode `20.24`, `880`, or the git hash `265e09c4a` under any
  tested interpretation (ASCII big/little endian, BCD, FLOAT32/64, UINT32),
  and the web UI exposes no firmware-like value matching them. 4116 is most
  likely an unrelated Nav10 data point that happens to sit at that address.
  Earlier drafts of this note speculated 4116 might be the firmware register;
  that hypothesis is **rejected** by the web-UI cross-check.
- Conclusion: on this Nav10 firmware there is **no reliable Modbus source
  for the firmware version** — the web UI is the only source. The
  `firmware_version` register should remain disabled by default; do not move
  it to 4116.

### Open Point 5 — external room temperatures 1650–1662 and active circuits

All seven external-room-temperature inputs (1650, 1652, 1654, 1656, 1658,
1660, 1662) return the **same** `-1.0` sentinel (`[0x0000, 0xBF80]`),

| F | 1403 | 0 | inactive/empty |
| G | 1405 | 0 | inactive/empty |

Findings:

- Every external room-temperature input reads `-1.0` regardless of whether
  its circuit is active (A, B are active; E/F/G are 0). The `-1.0` is the
  "no external sensor / not driven" state, not an active-circuit filter
  artefact: HKA (1650) is active yet still `-1.0`.
- This confirms the current active-circuit **filtering** behavior is a
  code-side model gate, not a device-side restriction — the device serves
  all seven addresses uniformly. The values are simply unpopulated because
  no external GLT room sensor is connected on this installation.
- No evidence that exposing HKB–HKG unconditionally would change behavior;
  they would just surface `-1.0` until an external sensor is wired. Keep
  the current active-circuit filtering unless a deployment specifically
  drives GLT room temperatures externally.

## Required evidence before any register-map change

Before changing register addresses, datatypes, sizes, function codes, model
inclusion, batching, or write behavior, collect at least one of:

1. An official IDM document/table for the exact register.
2. A hardware capture proving the exact behavior on the target firmware.

For every candidate register, record:

- firmware version shown by the local web UI
- heat pump model / Navigator generation
- Modbus register type
- function code
- start address
- register count
- raw response words
- decoded datatype and byte/word order
- write behavior, if any
- allowed range and sentinel values
- whether writes are EEPROM-sensitive or cyclically required
